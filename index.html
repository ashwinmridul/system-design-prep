Widget platform

Interviewer: design a widget. I treat it as a platform: hosts such as a Confluence page or a Jira issue run widgets built by us, partners, or a customer.

Requirements API Components Scale Wrap-up

Requirement gathering

About the first twelve minutes. I stay here until we agree the approach.

Questions, one at a time

  1. Who builds a widget?
  2. Where does it render?
  3. What may a widget do?
  4. What scale should I design for?
  5. Which permissions can it hold?
  6. Any hard bars?

If they tell me to decide

  • Partners install a widget onto a page inside our product.
  • A page can hold several widgets. Most are read-only. A few can write through our API.
  • The widget must not read the host page, the session cookie, or another widget.
  • Target: a large tenant, tens of widgets on a busy page, p95 interaction under two hundred milliseconds once loaded.

What I would say

  • A widget is a versioned bundle plus a manifest, installed on a host surface, rendered for the current user.
  • Our own teams ship it, so review can be stricter, and I still sandbox it so one widget cannot read the page.
  • Marketplace partners install it, so I treat the bundle as untrusted.
  • A customer's developers ship it, so the threat model is the same as a partner: untrusted code on a trusted page.
  • On a third-party site the frame gets no cookie and a public bridge origin. It cannot assume our page's content security policy.
  • It renders inside our product. The host owns the page, the slot, and the theme.
  • Where it also runs on a third-party site, the bridge checks origin on every message and the token is not our session cookie.
  • Most of the surface is read-only. The widget paints data the host already allowed.
  • A few widgets write back. Each write carries an idempotency key so a retry does not double-apply.
  • Dialogs and toasts go through the host. The widget asks. It does not open its own window over the page.
  • Display only means no write method on the bridge at all.
  • Scale is small: one to three widgets on a page for one team. I still cap frames, and I do not build a marketplace control plane yet.
  • A busy page holds about ten widgets. I lazy-mount them and cap how many frames stay live.
  • A large tenant can put tens of widgets on one page. Slots are virtualized, and frames that scroll away are unloaded.
  • The widget acts as the signed-in user, through a short-lived token scoped to this install and these permissions.
  • It does not inherit the user. An admin grants a fixed permission set, and the token cannot grow past that.
  • It holds no permissions. The bridge has no data request, only resize and a static render.
  • Accessibility is on both sides of the frame: the host slot and the widget's own tree.
  • Copy and layout come from the host locale, including right-to-left, not from hard-coded strings in the bundle.
  • Once loaded, a widget interaction stays under about two hundred milliseconds at the 95th percentile.
  • On a flaky network the cached bundle still paints, and the data is labeled stale.
  • The host owns navigation, theming, and permissions. The widget owns its own UI.
  • I would support view, resize, and a small set of host actions. I would not give it the DOM.
  • Edge cases: a widget that hangs, a permission the user does not have, a resize loop, and a host navigating away mid-call.

Two approaches

  • Same-origin script: fast and easy to theme, and one bug or one malicious widget can read the whole page. I would not ship that for partners.
  • Sandboxed iframe plus a message bridge: slower to start, and the host stays safe. Theming comes in as tokens, not shared CSS.

I would pick the sandbox. Does that match the threat model you want, before I go into the API?

API design and schema

About minute twelve to twenty-two.

Questions

  1. Is this read-heavy or write-heavy?
  2. Do widgets need live updates?
  3. Should it survive a flaky network?

Contract

  • Manifest: id, semantic version, bundle URL, permissions asked, and the sandbox flags.
  • Installation: host id, widget id, pinned version, and the admin's config.
  • Session: a short-lived token scoped to this install. Not the user's cookie.
  • There is no session token. The frame loads the bundle and stops.
  • I would load the manifest, the session, and the data over REST. A fresh load is enough. No stream.
  • I would load the manifest and the session over REST. Live data is server-sent events from the host, not a socket per widget.
  • I would poll the host every few seconds with a version token, and stop polling when the slot is off screen.
  • Writes are rare. They carry an idempotency key. A retry must not double-apply.
  • Writes are common, so the bridge batches them and every call is idempotent.
  • The contract has no write and no data read. Only ready and resize.
  • If the network drops, the cached bundle still renders and the data is labeled stale.
  • If the network drops, the slot shows a quiet unavailable state. I do not invent stale numbers.
  • Errors are a code plus a message the host can show. The widget never renders a raw stack.
  • Lists inside a widget are cursor-paginated. I would not let a widget pull an unbounded feed into the frame.
  • The bridge messages are typed: ready, resize, request, and result. I check the target origin on every message.

Scale-up and failures

About minute forty-two to fifty-two.

  • At ten times the widgets, I virtualize slots and unload frames that scroll far away.
  • If the BFF is down, installed widgets still render from the cached bundle and show stale data, clearly labeled.
  • One widget throwing is an error boundary around that slot. The page stays up.
  • A hot widget version can be killed by flag. Clients stop requesting that bundle.
  • I retry bridge calls with jitter, and I stop after a small budget so a loop cannot pin the CPU.

Wrap-up

Under two minutes.

  • We are hosting untrusted UI inside a trusted page, so isolation comes before features.
  • The design is a sandboxed frame, a typed bridge, and a short-lived scoped token.
  • We give up a bit of startup time and shared CSS, and we keep the host safe.
  • I would roll a widget version out behind a flag and watch crash rate and host INP before it is default.

UI component library

Interviewer: design a UI component library for our product teams.

Requirements API Components Scale Wrap-up

Requirement gathering

About the first twelve minutes.

Questions, one at a time

  1. Who consumes it?
  2. How many teams, and may they fork?
  3. Is theming one brand or several products?
  4. What is the accessibility and language bar?
  5. Server render, and what bundle budget?
  6. How painful may a breaking change be?

If they tell me to decide

  • Web only, many product teams, one brand with theming tokens for density and color mode.
  • Components must work with server rendering. No window access at import time.
  • Accessibility is WCAG AA, keyboard and screen reader included.
  • A breaking change needs a codemod and one version of overlap.

What I would say

  • The library is tokens plus primitives plus a few composed components. Docs and tests ship with it.
  • The public API is props and tokens. Class names and DOM structure are not a contract.
  • The first consumer is the web. Components stay free of platform APIs at import time.
  • Mobile shares the tokens and the props. The web DOM is not the contract a native app implements.
  • Email gets a separate, smaller set. I do not pretend a dialog works in a mail client.
  • One team owns every component. Other teams file a request. They do not publish a button.
  • Many teams contribute upstream. A new component needs a short proposal. Nobody forks the button.
  • Forks are allowed, so each fork is a named package with its own version. The shared button stays the default.
  • One brand. Density and color mode are tokens on a parent, not a second component set.
  • Several products share the components and pass their own token set. A product does not restyle with CSS overrides.
  • The bar is WCAG AA: keyboard, focus, name, and contrast, checked in CI.
  • Layout flips for right-to-left. I do not hard-code left and right in a component.
  • Strings come from the product, not from the component. A long translation cannot clip the control.
  • Imports are server-safe. Nothing touches window until the component mounts.
  • A button stays under about twenty kilobytes. A chart is a separate entry so the button page does not pay for it.
  • There is no tight cap, and I still split heavy components so a page pays only for what it renders.
  • The consumer is client-only. I can touch window in the module, and I still avoid a huge shared bundle.
  • A breaking change ships a codemod and one version where old and new overlap.
  • Two majors stay supported. The older one gets fixes only, and the guide says when it ends.
  • Breaking changes can ship in the next version. I still write the changelog, and I do not pretend it is additive.
  • Edge cases: a token rename, a nested interactive control, reduced motion, and a consumer still on the previous major.

Two approaches

  • Copy-paste into each app: fast to start, and the buttons drift apart within a quarter.
  • A versioned package with tokens as the contract: slower to change, and every product can upgrade on purpose.

I would pick the versioned package. Are you comfortable with that before I talk about the API of a component?

API design and schema

About minute twelve to twenty-two. Here the API is the component contract, not only HTTP.

Questions

  1. One package, or a package per component?
  2. Runtime theme switch, or build-time?
  3. Is there an HTTP API?

Contract

  • Tokens are data: color, space, type, radius, and motion. Components read variables, not hard-coded values.
  • Each component has a typed props list, a version, and a deprecation note if a prop is leaving.
  • I would ship one entry point so a deep import does not become a private API.
  • Each component is its own package, with a shared token package. A product installs only the buttons it uses.
  • A fork is another package, not a branch inside the shared one, so the default button stays installable.
  • Semantic versioning: a fix is safe, a feature is additive, and a major has a migration.
  • Versions still increment, and a minor may break. The changelog is the contract.
  • There is no product HTTP API. The contract is the package.
  • The docs site is a static catalog of examples. It is not on the product's critical path.
  • Telemetry, if we collect it, is adoption counts per component version, not user content.
  • I would rather have no runtime CSS-in-JS on the critical path. Static CSS keeps server render cheap.
  • The theme is compiled into the CSS. Switching brand means a rebuild, not a variable flip.

Collaborative editor

Interviewer: design an online editor, like a shared document, with more than one person typing.

Requirements API Components Scale Wrap-up

Requirement gathering

About the first twelve minutes. Conflict handling usually becomes the heart of this round.

Questions, one at a time

  1. How many people, and plain text or rich?
  2. Comments, suggestions, live cursors?
  3. Offline, or only while connected?
  4. How large, and who can edit?
  5. Keystroke to other screens?
  6. Regions, residency, or audit?

If they tell me to decide

  • Rich text, tens of concurrent editors, thousands of daily active users on popular docs.
  • Live cursors, comments anchored to text, and offline edits that sync later.
  • View and edit are different permissions, checked on every change.
  • Other people see a keystroke within about two hundred milliseconds on a healthy network.

What I would say

  • A document is a list of blocks. Text inside a block is the part we merge. Images and tables are blocks with their own ids.
  • Plain text, a handful of editors. A CRDT is still the merge, and the DOM can be the whole doc.
  • Rich text, tens of editors. I virtualize blocks and I batch remote paints to a frame.
  • About a hundred people in one doc. Presence is sampled, and viewers who cannot edit do not sit on the full op fan-out.
  • Cursors and presence are ephemeral. They are not part of the saved document.
  • Comments anchor to a stable id inside the text, not to a character offset that drifts.
  • A suggestion is an op the author can accept. Until then it is visible and it is not the document.
  • Offline edits sit locally and sync later. The user can see they have not reached anyone else yet.
  • There is no offline log. If the socket is down, typing is disabled and I say we will reconnect.
  • View and edit are different permissions, checked on the server for every change.
  • A long doc opens from a snapshot plus a window of blocks. I do not build the whole DOM.
  • Anyone who can open the doc can edit. I still check that they can open it, on every op.
  • Other people should see a keystroke within about a hundred milliseconds on a healthy network. I paint my own character immediately.
  • Other people should see a keystroke within about two hundred milliseconds. My own character paints before the round trip.
  • About a second is acceptable for other screens. I still paint locally first so my typing never waits.
  • One region is enough. I do not split the op log across continents.
  • The snapshot and the op log stay in the region we chose for that tenant.
  • An audit log records who changed the doc and when. It is not the CRDT payload itself.
  • Non-functional: merge without data loss, permission checks on the server, and a snapshot so we do not replay the full history on open.
  • Edge cases: two people delete the same word, a comment on text that was cut, offline edits that overlap, and a viewer who must not receive the ops.

Two approaches

  • Operational transformation: the server orders every op. Clients transform against that order. It is proven, and offline is awkward because the client needs the server's place in line.
  • A CRDT per block: each client can edit offline and merge later without a central order. Payloads are a bit larger, and the model is easier to reason about when the network drops.

I would pick a CRDT for the text, plus a server snapshot every so often. Last-write-wins is only for fields like the title. Does that split sound right?

API design and schema

About minute twelve to twenty-two.

Questions

  1. What is the hot path?
  2. Where does presence go?
  3. How long may a client be offline?

Contract

  • Document: id, ACL, snapshot version, and title. Title uses a version number, not the CRDT.
  • Op: document id, client id, a CRDT id, and the payload. The server stores it and fans it out. It does not rewrite it.
  • Open is REST: snapshot plus the ops since that snapshot. Live edits are a WebSocket.
  • There is no op stream. The client sends a new snapshot, and last-write-wins on the version number. Two editors can lose a paragraph.
  • I would not put cursors on the durable log. Presence is a side channel with a short time to live.
  • Presence shares the document socket and is marked ephemeral, so a replay of the log skips it.
  • If the socket drops, the client resumes from the last op id. After a few minutes it fetches a new snapshot.
  • A client can be offline for hours. It sends a batch of ops with client ids, and the CRDT merges them.
  • There is no offline batch. A dropped socket means reload from the latest snapshot.
  • The server rejects an op when the user lost edit permission, even if they loaded the doc earlier.
  • The server rejects an op only when the user can no longer open the doc.
  • Images upload to object storage. The document stores the id, not the bytes.

Messenger

Interviewer: design a messenger, in the shape of Slack. Channels, direct messages, and history.

Requirements API Components Scale Wrap-up

Requirement gathering

About the first twelve minutes.

Questions, one at a time

  1. Channels, direct messages, threads?
  2. What scale?
  3. Presence, typing, reactions, files?
  4. Is history searchable here?
  5. Offline sends?
  6. Retention, audit, or encryption?

If they tell me to decide

  • Work chat. The server can read messages so we can search and meet compliance later.
  • Channels and threads. Presence and typing are best-effort.
  • History is paged. Search is a separate index, not the hot path.
  • A client may queue a send for a few minutes offline. It is not a full offline product.

What I would say

  • A channel is an ordered log. A direct message is a channel with two members.
  • A thread is a log with a parent message id.
  • The client generates the message id so a retry cannot post twice.
  • Unread state and the log are server-owned. The UI may paint ahead, then reconcile.
  • A small workspace can keep a short page in memory. I still page history.
  • Thousands of people and long channels. The screen holds one window, and the list is virtualized.
  • Tens of thousands of people. Fan-out of a hot channel is sharded, and presence is sampled.
  • Presence and typing are best-effort. Losing them is fine. Losing a message is not.
  • A reaction is a small write on the message id, idempotent per user and emoji.
  • A file uploads to object storage. The message stores the id, and the scan finishes before the file is downloadable.
  • Search is a follower index. It is not on the send path.
  • Search is in this design: the send path still only writes the log, and an indexer reads it.
  • A client may queue a send for a few minutes. It is not a full offline product.
  • If the socket is down, send is disabled. I do not queue.
  • Retention deletes or tombstones messages after the policy window. The sequence still has a gap the client can skip.
  • An audit log records who posted and who exported. It is separate from the channel log.
  • End-to-end encryption means the server cannot search or meet a content audit. I would say that tradeoff out loud before I pick it.
  • Search and end-to-end encryption do not both work. I would keep search and drop encryption, unless they insist, in which case search is only on the device.
  • Non-functional: order per channel, reconnect without a gap or a duplicate, and a virtualized list so a long channel stays cheap.
  • Edge cases: send during a reconnect, two devices on one user, a message deleted while visible, and a channel the user just lost access to.

Two approaches

  • Poll the latest page: simple, and it feels late and wasteful at chat scale.
  • REST for history, a WebSocket for new events, resume from the last sequence. If the gap is large, throw the buffer away and refetch.

I would pick REST plus a socket with a sequence number. Is search in scope, or may I leave it as a follower system?

Cookie banner

Interviewer: design an accept-or-reject cookie banner. Compliance and performance both matter.

Requirements API Components Scale Wrap-up

Requirement gathering

Two approaches

  • Pure fan-out on write: every follower gets the card pushed into a precomputed feed. Fast to read, and a popular author is an expensive write.
  • Pure fan-in on read: store the events and build the page when I open the feed. Cheap to write, and the open gets slow.

I would push to recently active followers and build the page on read for everyone else. Does a minute of lag on the feed bother you?
