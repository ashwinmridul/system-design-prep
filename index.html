System design, as I would say it

One problem per tab. I ask one question, wait, and note the answer. Then I speak the lines under it. Tap an abbreviation for the full form. The minute marks are a soft guide, not a clock to chase. Swipe the tabs sideways on a phone.

Once, at the start of the round

I'll structure this as requirements and approach, then API and schema, component design and scalability, scale-up and failures, and a short wrap-up with tradeoffs. If I go too deep anywhere, please interrupt me. I want all five steps inside the hour.

Widget platform

Interviewer: design a widget. I treat it as a platform: hosts such as a Confluence page or a Jira issue run widgets built by us, partners, or a customer.

Requirements API Components Scale Wrap-up

Requirement gathering

About the first twelve minutes. I stay here until we agree the approach.

Questions, one at a time

  1. Who builds a widget: our teams, marketplace partners, or a customer's own developers?
  2. Where does it render: inside our products, on a third-party site, or both?
  3. What may a widget do: show data, write back, open dialogs, or only display?
  4. What scale should I design for: widgets per page, installs per tenant, and daily active users?
  5. Does the widget act as the signed-in user, and which permissions can it hold?
  6. Any hard bars for accessibility, internationalization, latency, or offline use?

If they tell me to decide

  • Partners install a widget onto a page inside our product.
  • A page can hold several widgets. Most are read-only. A few can write through our API.
  • The widget must not read the host page, the session cookie, or another widget.
  • Target: a large tenant, tens of widgets on a busy page, p95 interaction under two hundred milliseconds once loaded.

What I would say

  • A widget is a versioned bundle plus a manifest, installed on a host surface, rendered for the current user.
  • The host owns navigation, theming, and permissions. The widget owns its own UI.
  • I would support view, resize, and a small set of host actions such as a toast or a dialog. I would not give it the DOM.
  • Non-functional: isolation, a performance budget per widget, accessibility on both sides of the frame, and a kill switch per version.
  • Edge cases: a widget that hangs, a widget that asks for a permission the user does not have, a resize loop, and a host navigating away mid-call.

Two approaches

  • Same-origin script: fast and easy to theme, and one bug or one malicious widget can read the whole page. I would not ship that for partners.
  • Sandboxed iframe plus a message bridge: slower to start, and the host stays safe. Theming comes in as tokens, not shared CSS.

I would pick the sandbox. Does that match the threat model you want, before I go into the API?

API design and schema

About minute twelve to twenty-two.

Questions

  1. Is this read-heavy, with a few writes, or do widgets mutate host data often?
  2. Do widgets need live updates, or is a fresh load enough?
  3. Should a widget keep working on a flaky network?

Contract

  • Manifest: id, semantic version, bundle URL, permissions asked, and the sandbox flags.
  • Installation: host id, widget id, pinned version, and the admin's config.
  • Session: a short-lived token scoped to this user, this install, and these permissions. Not the user's cookie.
  • I would load the manifest and the session over REST. Live data, if we need it, is SSE from the host, not a socket per widget.
  • Writes carry an idempotency key. A retry must not double-apply.
  • Errors are a code plus a message the host can show. The widget never renders a raw stack.
  • Lists inside a widget are cursor-paginated. I would not let a widget pull an unbounded feed into the frame.
  • The bridge messages are typed: ready, resize, request, and result. I check the target origin on every message.

Component design and scalability

About minute twenty-two to forty-two. This is the long drawing section.

Questions

  1. Is the host one app, or several products sharing one widget runtime?
  2. Do we already have a design system the widget should consume as tokens?
Host page→Widget slots→Bridge→Sandboxed iframe→BFF→Product APIs
  • While I draw: the page never shares its DOM with the widget. The bridge is the only door.
  • I lazy-mount a widget when it nears the viewport, and I cap how many frames are live.
  • I would not set both allow-scripts and allow-same-origin. Together they weaken the sandbox.
  • State split: the host holds install and theme. The widget holds its own view state inside the frame.
  • Cache: manifest and bundle on the CDN, session token in memory only, host config in memory with a short TTL.
  • A feature flag can disable one widget version without a host deploy. The slot then shows a quiet fallback.
  • The bottleneck is memory and long tasks from many frames. The budget is bundle size plus a long-task limit.
  • I would watch load time, bridge errors, and crash rate per widget version, with an SLO on host-page INP.

Scale-up and failures

About minute forty-two to fifty-two.

  • At ten times the widgets, I virtualize slots and unload frames that scroll far away.
  • If the BFF is down, installed widgets still render from the cached bundle and show stale data, clearly labeled.
  • One widget throwing is an error boundary around that slot. The page stays up.
  • A hot widget version can be killed by flag. Clients stop requesting that bundle.
  • I retry bridge calls with jitter, and I stop after a small budget so a loop cannot pin the CPU.

Wrap-up

Under two minutes.

  • We are hosting untrusted UI inside a trusted page, so isolation comes before features.
  • The design is a sandboxed frame, a typed bridge, and a short-lived scoped token.
  • We give up a bit of startup time and shared CSS, and we keep the host safe.
  • I would roll a widget version out behind a flag and watch crash rate and host INP before it is default.

UI component library

Interviewer: design a UI component library for our product teams.

Requirements API Components Scale Wrap-up

Requirement gathering

About the first twelve minutes.

Questions, one at a time

  1. Who consumes it: web only, or also mobile and email?
  2. How many teams, and can a team fork a component or only contribute upstream?
  3. Is theming one brand, or several products on the same components?
  4. What is the accessibility bar, and do we support right-to-left and multiple languages?
  5. Must components render on the server, and what is the bundle budget?
  6. How painful may a breaking change be?

If they tell me to decide

  • Web only, many product teams, one brand with theming tokens for density and color mode.
  • Components must work with server rendering. No window access at import time.
  • Accessibility is WCAG AA, keyboard and screen reader included.
  • A breaking change needs a codemod and one version of overlap.

What I would say

  • The library is tokens plus primitives plus a few composed components. Docs and tests ship with it.
  • The public API is props and tokens. Class names and DOM structure are not a contract.
  • I would not let every team publish a button. A new component needs a short proposal.
  • Non-functional: tree-shaking, server-safe imports, visual regression, and an accessibility check in CI.
  • Edge cases: a token rename, a nested interactive control, reduced motion, and a consumer still on the previous major.

Two approaches

  • Copy-paste into each app: fast to start, and the buttons drift apart within a quarter.
  • A versioned package with tokens as the contract: slower to change, and every product can upgrade on purpose.

I would pick the versioned package. Are you comfortable with that before I talk about the API of a component?

API design and schema

About minute twelve to twenty-two. Here the API is the component contract, not only HTTP.

Questions

  1. Do consumers install one package, or can they depend on a single component?
  2. Do we need a runtime theme switch, or is theming build-time?
  3. Is there an HTTP API at all, or only the package?

Contract

  • Tokens are data: color, space, type, radius, and motion. Components read variables, not hard-coded values.
  • Each component has a typed props list, a version, and a deprecation note if a prop is leaving.
  • I would ship one entry point so deep imports do not become a private API.
  • Semantic versioning: fix is safe, feature is additive, major has a codemod.
  • The docs site is a small REST or static catalog of examples. It is not on the product's critical path.
  • Telemetry, if we collect it, is adoption counts per component version, not user content.
  • I would rather have no runtime CSS-in-JS on the critical path. Static CSS keeps server render cheap.

Component design and scalability

About minute twenty-two to forty-two.

Questions

  1. One design-system team, or each product squad contributing?
  2. Are we wrapping this around an existing visual language, or starting clean?
Tokens→Primitives→Components→Product app→Docs and visual tests
  • While I draw: products depend on the package. They do not copy the source.
  • Primitives are button, text field, dialog. Composed pieces such as a picker sit on top and can lag a version.
  • State stays inside the component unless the caller needs it. I would not force a global store.
  • Theme is a set of CSS variables on a parent. Switching color mode does not reload the app.
  • I would code-split the docs, not the button. The button must be in the main bundle only if the page uses it.
  • The bottleneck at scale is upgrade pain, not QPS. Codemods and visual diffs are the scale plan.
  • CI runs accessibility checks and screenshot diffs per component. A contrast regression fails the build.

Scale-up and failures

About minute forty-two to fifty-two.

  • A hundred teams: I keep one major in support and publish a migration guide, not a long-lived fork.
  • If the package registry is down, apps keep the version they already installed. Runtime does not phone home.
  • A bad release is yanked and the previous version stays installable. Feature flags do not belong inside a button.
  • A heavy component is split so a page that only needs a button does not download a chart.

Wrap-up

Under two minutes.

  • The library is a contract between teams, so the API and the upgrade path matter more than any single component.
  • Tokens, a versioned package, and CI that catches accessibility and visual drift.
  • We move slower on purpose, and we stop shipping five different buttons.
  • I would measure adoption by version and time-to-upgrade, and treat a stuck major as a defect.

Collaborative editor

Interviewer: design an online editor, like a shared document, with more than one person typing.

Requirements API Components Scale Wrap-up

Requirement gathering

About the first twelve minutes. Conflict handling usually becomes the heart of this round.

Questions, one at a time

  1. How many people edit the same doc at once, and is it text only or rich content?
  2. Do we need comments, suggestions, and live cursors?
  3. Must it work offline, or only while the socket is up?
  4. How large is a document, and is there a permission difference between view and edit?
  5. What latency do we want from keystroke to other people's screens?
  6. Are there regions, data residency, or audit requirements?

If they tell me to decide

  • Rich text, tens of concurrent editors, thousands of daily active users on popular docs.
  • Live cursors, comments anchored to text, and offline edits that sync later.
  • View and edit are different permissions, checked on every change.
  • Other people see a keystroke within about two hundred milliseconds on a healthy network.

What I would say

  • A document is a list of blocks. Text inside a block is the part we merge. Images and tables are blocks with their own ids.
  • Cursors and presence are ephemeral. They are not part of the saved document.
  • Comments anchor to a stable id inside the text, not to a character offset that drifts.
  • Non-functional: merge without data loss, permission checks on the server, and a snapshot so we do not replay the full history on open.
  • Edge cases: two people delete the same word, a comment on text that was cut, offline edits that overlap, and a viewer who must not receive the ops.

Two approaches

  • Operational transformation: the server orders every op. Clients transform against that order. It is proven, and offline is awkward because the client needs the server's place in line.
  • A CRDT per block: each client can edit offline and merge later without a central order. Payloads are a bit larger, and the model is easier to reason about when the network drops.

I would pick a CRDT for the text, plus a server snapshot every so often. Last-write-wins is only for fields like the title. Does that split sound right?

API design and schema

About minute twelve to twenty-two.

Questions

  1. Is the hot path the live op stream, with snapshots as the cold path?
  2. Should presence share the document socket or stay separate?
  3. How long may a client be offline before we ask them to reload?

Contract

  • Document: id, ACL, snapshot version, and title. Title uses a version number, not the CRDT.
  • Op: document id, client id, a CRDT id, and the payload. The server stores it and fans it out. It does not rewrite it.
  • Open is REST: snapshot plus the ops since that snapshot. Live edits are a WebSocket.
  • I would not put cursors on that same durable log. Presence is a side channel with a short TTL.
  • If the socket drops, the client resumes from the last op id. If it is too far behind, it fetches a new snapshot.
  • A save from offline is a batch of ops with client ids, so a retry is idempotent.
  • The server rejects an op when the user lost edit permission, even if they loaded the doc earlier.
  • Images upload to object storage. The document stores the id, not the bytes.

Component design and scalability

About minute twenty-two to forty-two.

Questions

  1. One editor codebase, or several products embedding it?
  2. Do comments and the doc canvas ship as one bundle?
Editor shell→Block list→CRDT model→Op log→Snapshot store
  • While I draw: the screen shows a window of blocks. The model can be larger than the DOM.
  • Local typing updates the model first, then the socket. I do not wait for a round trip to paint my own character.
  • Undo is a local stack of inverse ops, not a global undo that would surprise the other author.
  • Offline ops sit in IndexedDB and flush on reconnect. The UI shows they are pending.
  • I virtualize blocks so a long page does not create thousands of nodes.
  • The bottleneck is applying a burst of remote ops on the main thread. I batch paints to a frame.
  • I would watch op apply time, socket lag, and failed permission checks, with an SLO on keystroke latency.

Scale-up and failures

About minute forty-two to fifty-two.

  • A very large doc: snapshot plus a window of blocks. I do not replay ten years of ops on open.
  • If the socket service is down, I keep local edits queued and say we will sync. I do not pretend others can see them.
  • If two offline clients conflict, the CRDT merges the text. I surface a comment only if its anchor survived.
  • A hot document with hundreds of viewers: presence is sampled, and read-only viewers do not join the op fan-out at full rate. They can poll a snapshot.
  • I would kill a bad client build with a flag if it starts sending ops the server must reject.

Wrap-up

Under two minutes.

  • The hard part is concurrent text, not the toolbar.
  • CRDT inside blocks, snapshots for open, a separate channel for cursors, permissions on every op.
  • We accept larger ops than classic OT, and we get offline merge without a central transform.
  • I would ship it behind a flag on one product surface and watch keystroke latency and merge errors.

Messenger

Interviewer: design a messenger, in the shape of Slack. Channels, direct messages, and history.

Requirements API Components Scale Wrap-up

Requirement gathering

About the first twelve minutes.

Questions, one at a time

  1. Is this workspace chat: channels, direct messages, and threads?
  2. What scale: people per workspace, messages per channel, concurrent connections?
  3. Do we need presence, typing, reactions, and file attachments?
  4. Is history searchable in this design, or is search a later system?
  5. Offline sends, or only live while connected?
  6. Any end-to-end encryption, retention, or audit requirement?

If they tell me to decide

  • Work chat. The server can read messages so we can search and meet compliance later.
  • Channels and threads. Presence and typing are best-effort.
  • History is paged. Search is a separate index, not the hot path.
  • A client may queue a send for a few minutes offline. It is not a full offline product.

What I would say

  • A channel is an ordered log. A thread is a log with a parent message id.
  • The client generates the message id so a retry cannot post twice.
  • Unread state and the log are server-owned. The UI may paint ahead, then reconcile.
  • Non-functional: order per channel, reconnect without a gap or a duplicate, and a virtualized list so a long channel stays cheap.
  • Edge cases: send during a reconnect, two devices on one user, a message deleted while visible, and a channel the user just lost access to.

Two approaches

  • Poll the latest page: simple, and it feels late and wasteful at chat scale.
  • REST for history, a WebSocket for new events, resume from the last sequence. If the gap is large, throw the buffer away and refetch.

I would pick REST plus a socket with a sequence number. Is search in scope, or may I leave it as a follower system?

API design and schema

About minute twelve to twenty-two.

Questions

  1. Read-heavy history, write-light sends. Does that match how you see it?
  2. Should typing and presence be durable at all?
  3. How should we paginate: newest window first?

Contract

  • Message: client UUID, channel id, optional thread id, body, server sequence, and time.
  • Membership and unread cursors are their own resources. I do not hide them inside the message.
  • GET history with a cursor. POST message with the client id as the idempotency key.
  • The socket emits message created, message updated, and a resume token. Typing is a separate ephemeral event, throttled.
  • Presence is a heartbeat with a TTL around half a minute. I would not store it next to messages.
  • Errors: a 409 on a duplicate client id returns the original message. A 403 means drop it from the outbox and say it was not allowed.
  • Attachments upload first. The message references the file id.
  • I would not put message bodies in a push payload. The push carries an id, and the client fetches.

Component design and scalability

About minute twenty-two to forty-two.

Questions

  1. One web app, or also a desktop shell around the same client?
  2. Is the message list virtualized from day one?
Channel list→Message window→Outbox→REST history→WebSocket
  • While I draw: the screen holds one channel window, not the whole history.
  • Sending paints the bubble immediately with a pending mark, then replaces it when the server sequence arrives.
  • The outbox lives in memory and in IndexedDB so a refresh does not lose a pending send.
  • I virtualize rows. Images and link previews lazy-load.
  • If the socket falls behind, I resync from REST instead of applying a huge burst on the main thread.
  • Cache: the latest page of the open channel in memory, older pages discarded as you scroll away.
  • I would watch send latency, reconnect gaps, and duplicate rate, with an SLO on time-to-first-message for the open channel.

Scale-up and failures

About minute forty-two to fifty-two.

  • A channel with a huge membership: fan-out is by subscription to that channel, not to every user in the company.
  • If the socket tier is down, history still loads and sends queue. I say live updates are paused.
  • If history is down, I show the messages I already have and disable scroll-back rather than a blank screen.
  • A hot channel: coalesce typing events and cap presence updates so they cannot drown real messages.
  • I retry sends with jitter and the same client id. I do not mint a new id on retry.

Wrap-up

Under two minutes.

  • Chat is an ordered log plus a live tail, with identity on the client so retries are safe.
  • REST for the past, a sequenced socket for the present, ephemeral events kept off the log.
  • We do not promise full offline, and we do not pretend search is the same pipeline.
  • I would roll the socket resume out by workspace and watch duplicate sends and gap repairs.

Cookie banner

Interviewer: design an accept-or-reject cookie banner. Compliance and performance both matter.

Requirements API Components Scale Wrap-up

Requirement gathering

About the first twelve minutes. This problem is won on scope and on not hurting the page.

Questions, one at a time

  1. Which regions, and is consent opt-in, opt-out, or both depending on the region?
  2. What categories: strictly necessary, functional, analytics, marketing?
  3. Who is the user: anonymous visitor, signed-in account, or both?
  4. Must reject be as easy as accept, and can they change their mind later?
  5. What may we set before a choice, and what scripts must wait?
  6. Any budget for LCP, CLS, and the size of the consent code?

If they tell me to decide

  • GDPR-style opt-in for analytics and marketing. Necessary cookies only before a choice.
  • Accept and reject are equally visible. A link reopens the choice later.
  • The banner is an overlay. It must not shift the page and must not be the LCP element.
  • A policy change bumps a version and asks again.

What I would say

  • Consent is a record: who or which device, which policy version, which region, which categories, and when.
  • The page ships a tiny gate. Non-essential tags do not run until that record says yes.
  • Necessary cookies cover the session, the load balancer, and storing this choice. Nothing else.
  • Non-functional: the gate is inline and small, the dialog is keyboard accessible, and a late policy fetch cannot block first paint.
  • Edge cases: a choice on one device, Global Privacy Control already set, a child region with a stricter default, and a user who rejects and then signs in.

Two approaches

  • A third-party consent script in the head: easy to buy, and it competes with LCP and can run late.
  • A first-party stub in the HTML that reads a local record, renders the choice, and only then loads tags. The policy text can revalidate after paint.

I would pick the first-party stub. Is equal-weight reject a requirement I should treat as fixed?

API design and schema

About minute twelve to twenty-two.

Questions

  1. Is the record anonymous until sign-in, and do we merge it after?
  2. Do we need real time here at all?
  3. Should the policy be cached at the edge?

Contract

  • Policy: version, region, categories, and the legal text URL. Cached on the CDN.
  • Record: subject id, policy version, region, choices map, timestamp, and source such as banner or GPC.
  • GET policy is cacheable. POST choice is idempotent for the same subject and version.
  • No WebSocket. This is a rare write. Polling would be wasteful.
  • The stub reads a first-party cookie or local record so a refresh does not ask again.
  • If POST fails, I keep the choice locally and retry. I do not start marketing tags until the post succeeds or the local record is enough for our policy. I would ask which of those you prefer. My default is: do not start tags until we have a stored yes.
  • Signed-in merge is a POST that attaches the anonymous record to the account, once.
  • Errors are quiet. A failed policy fetch falls back to the policy we shipped, which is the strict one.

Component design and scalability

About minute twenty-two to forty-two.

Questions

  1. One banner component across products, from the design system?
  2. Do analytics tags live in a tag manager we must gate?
HTML stub→Local record→Banner→Choice API→Tag gate
  • While I draw: tags sit behind the gate. The banner does not sit in the document flow.
  • The dialog traps focus, labels both buttons, and restores focus when it closes.
  • I would not animate the banner in a way that moves layout. CLS stays near zero.
  • Copy comes from the policy version so legal can change text without a client release, after the first paint.
  • A feature flag can force the strict default if a region rollout is wrong.
  • The bottleneck is render-blocking script, not QPS. The stub stays tiny.
  • I would watch banner shown rate, choice latency, and LCP with and without the banner, plus a count of tags that fired with no yes.

Scale-up and failures

About minute forty-two to fifty-two.

  • A traffic spike does not change the design. The policy is static at the edge. The choice write is small.
  • If the choice API is down, I keep the decision on the device and retry. Tags stay off until we know.
  • If the CDN policy is stale, the shipped strict default still protects us. A version bump asks again.
  • A bad tag that ignores the gate is a kill switch on that tag id.
  • I would not retry in a tight loop. A few tries with jitter are enough.

Wrap-up

Under two minutes.

  • The banner is a gate on scripts, not a modal we hope people click.
  • A first-party stub, a versioned policy, equal accept and reject, tags only after a stored yes.
  • We give up a convenient third-party loader, and we keep LCP and consent honest.
  • I would ship region by region behind a flag and alert if any non-essential tag fires without a yes.

Jira board

Interviewer: design a board. Columns, cards, drag and drop, more than one person on it. I treat it as a Jira board: a view over issues, not a second store of the issues.

Requirements API Components Scale Wrap-up

Requirement gathering

About the first twelve minutes.

Questions, one at a time

  1. Is a column a status, a swimlane, or something the user defines?
  2. How many issues can sit on one board, and how many people move cards at once?
  3. Do filters run on the client or on the server?
  4. Is order inside a column meaningful, and can two people drag the same card?
  5. Do we need live updates, offline edits, or both?
  6. Any WIP limit, permission per issue, or accessibility requirement for drag and drop?

If they tell me to decide

  • Columns are statuses. Rank inside a column is explicit.
  • A board can see tens of thousands of matching issues. The client holds a window, not all of them.
  • Filters are server-side. Live updates are on. Offline drag is not.
  • Keyboard must be able to move a card. Drag is not the only path.

What I would say

  • The board is a query plus a window per column. The issue store remains the source of truth.
  • A move changes status, rank, or both. Rank is a key between neighbors so I do not renumber the column.
  • I paint the drop immediately, then confirm. If the server disagrees, I put the card back and refetch that window.
  • Non-functional: p95 move confirm under a few hundred milliseconds, no long task while dragging, and stable keyboard order.
  • Edge cases: two drags of one card, a filter that hides the card mid-drag, a transition the workflow forbids, and a column that fails while others load.

Two approaches

  • Load every matching issue and group them in the browser. Fine for a small board, and it falls over on a real project.
  • Each column asks for a ranked window. Drag posts a rank between two ids. Live events patch a card or tell that column to refetch.

I would pick windows and a rank key. Should a forbidden workflow transition be rejected by the server even if the UI allowed the drop?

API design and schema

About minute twelve to twenty-two.

Questions

  1. Is the read path the column window, and the write path a single rank or transition call?
  2. Do we push issue events, or is a short poll acceptable?
  3. How fresh must a card be if someone edits it on the issue page?

Contract

  • Board: id, filter, and the column definitions. It does not embed every issue.
  • Card: issue id, summary, status, rank key, and the few fields the card paints.
  • GET a column with a cursor. POST a move with before-id, after-id, and an idempotency key.
  • I would use a WebSocket or SSE for issue-updated events that match this board's filter. Polling every second will not scale.
  • A 409 means the neighbors changed. The client refetches the window instead of guessing a new rank.
  • A 422 means the workflow rejected the status change. The card animates back.
  • Filter changes cancel the in-flight windows and start over. I do not append a new filter onto old cards.
  • Permissions are applied on the query. A card I cannot see is absent, not a locked placeholder, unless you want that leak. I would keep it absent.

Component design and scalability

About minute twenty-two to forty-two.

Questions

  1. Is this one board experience, or embedded in several products?
  2. Do we share the card component with the issue list?
Board shell→Column window→Card→Rank API→Issue events
  • While I draw: each column is its own list with its own cursor. The shell owns the filter.
  • UI state, such as which card is grabbed, stays local. Server state is the issue cache, patched by id.
  • I virtualize rows inside a column. Off-screen cards are not in the DOM.
  • Optimistic state is marked so a slow confirm does not let me drag the same card again.
  • A flag can disable live updates and leave the board on manual refresh if the event stream misbehaves.
  • The bottleneck is rendering and event storms, not the drag gesture itself.
  • I would watch move-confirm latency, conflict rate, and long tasks during drag, plus an SLO on time-to-interactive for the first window.

Scale-up and failures

About minute forty-two to fifty-two.

  • A million matching issues never enter the client. Deeper scroll asks for the next window.
  • If the issue API is down, I show the last windows I have, disable drag, and say the board is read-only.
  • If one column errors, the others stay. That column gets a retry.
  • Two people drop the same card: the server orders the writes. The loser refetches. I do not merge ranks on the client.
  • A noisy event stream: I coalesce patches per issue per frame, and I back off if I am applying more events than I can paint.

Wrap-up

Under two minutes.

  • A board is a windowed view, not a copy of the issue database.
  • Rank between neighbors, optimistic move, server as the judge, live patches by issue id.
  • We give up dragging through the entire backlog offline, and we keep the client small.
  • I would enable live updates per project and watch conflict rate and long tasks.

Permissioned search

Interviewer: design search across a tenant's Jira issues and Confluence pages. Results have to be fast, ranked, and only what this person is allowed to see.

Requirements API Components Scale Wrap-up

Requirement gathering

About the first twelve minutes. I would name the permission rule before I talk about ranking.

Questions, one at a time

  1. What is in the index: issues, pages, comments, attachments?
  2. How large is a tenant, and what is the latency bar for typeahead versus a full results page?
  3. If someone loses access, how fast must that hit disappear?
  4. May we show "you cannot open this", or must a forbidden hit be invisible?
  5. Do we need facets, filters, and highlighting?
  6. Is ranking keyword, recency, or personal?

If they tell me to decide

  • Issues and pages, per tenant. A big tenant can have millions of issues.
  • Typeahead under about three hundred milliseconds. A full page under a second, at p95.
  • A forbidden document is invisible, including its title. Facets must not leak it either.
  • A deprovision or a permission change should drop the hit within seconds, not on the next full reindex.

What I would say

  • The client is not the place that enforces permissions. It only renders what the server already allowed.
  • I would rather over-fetch candidates and filter them with a fresh permission check than trust a stale pre-filtered index.
  • Highlighting is computed on the server so we do not ship the whole document to bold a word.
  • Non-functional: tenant isolation, a short TTL on permission cache, and cancel-on-type in the UI.
  • Edge cases: a user removed mid-session, a grant that changed an hour ago, a query that matches only forbidden docs, and a facet count that would reveal a private project.

Two approaches

  • Index a copy of the content per user. Reads are simple, and writes explode. A permission change rewrites a huge slice of the index.
  • One index per tenant, retrieve candidates, then authorize and fill the page. Writes stay sane. The query does a bit more work, and I over-fetch so the page is not short after filtering.

I would pick tenant index plus a permission check at query time. Is "invisible, not locked" the right product rule?

API design and schema

About minute twelve to twenty-two.

Questions

  1. Are suggest and full search two endpoints with different budgets?
  2. How stale may the index be, in seconds?
  3. Do we paginate with a cursor so ranking does not skip or repeat?

Contract

  • Query: text, types, filters, cursor, and a limit. Response: hits with id, type, title, snippet, rank, and the next cursor.
  • I would not return a score the user can use to infer hidden documents. The cursor is opaque.
  • Suggest is a tighter limit, no facets. Full search can include facets that were counted after authorization.
  • REST is enough. I debounce and abort the previous request. A socket is not worth it for typing.
  • The permission cache key includes a version. Deprovision bumps that version so old cache entries miss.
  • If authorization filters too many hits, the server fetches another candidate batch before it returns a short page.
  • Errors: timeout returns a retryable error. I do not show a cached result from another user.
  • The client cache is only for back navigation in this session, and it is keyed by user. It is not a source of truth.

Component design and scalability

About minute twenty-two to forty-two.

Questions

  1. Is the box a global header, a page, or both sharing one client?
  2. Do we already have a design-system combobox?
Search box→BFF→Tenant index→Authz→Hits
  • While I draw: authz sits after the index and before the response. The browser never sees the candidate list.
  • The box waits about a hundred and fifty milliseconds after the last key, then sends. A new key aborts the last call.
  • The list is a combobox: keyboard, active descendant, and a status line for result count.
  • I keep server state for the result set and local state for the query text and highlight.
  • Index lag is honest. If we know the index is behind, I say results may be a few seconds old.
  • The bottleneck at tenant scale is the index plus authz fan-out, not rendering twenty rows.
  • I would watch p95 by endpoint, empty-page rate after authz, and any hit opened that returns 403. A 403 on open is a defect.

Scale-up and failures

About minute forty-two to fifty-two.

  • Ten million issues: the index is per tenant, sharded. The client still asks for one page.
  • If search is down, the box says search is unavailable. I do not fall back to a client-side scan.
  • If authz is slow, I would rather time out than return unchecked hits.
  • A hot tenant: cache popular queries briefly, but never across users, and never past a permission-version bump.
  • I limit in-flight requests to one suggest call. That avoids a thundering herd from a fast typist.

Wrap-up

Under two minutes.

  • This is a permission problem that has to feel like search.
  • Tenant index, authorize at query time, invisible misses, a client that only types, aborts, and renders.
  • We spend more on each query, and we do not leak a title or rewrite the index on every grant change.
  • I would ship suggest first, alert on 403-after-click, and keep the permission TTL short.

Notification center

Interviewer: design notifications. I focus on the in-app center: the bell, the list, and the unread count. Email and mobile push are workers fed by the same event.

Requirements API Components Scale Wrap-up

Requirement gathering

About the first twelve minutes.

Questions, one at a time

  1. Which events: comments, mentions, assignments, edits, or all of them?
  2. Who receives one: the actor's watchers, the page watchers, or a team?
  3. Do we collapse many edits of one page into a single row?
  4. Channels in scope: in-app only, or email and push as well?
  5. What is unread: a count, a dot, or a full list that must be exact?
  6. Preferences, quiet hours, and how fast the bell must move?

If they tell me to decide

  • In-app is the product I design. Email is another consumer of the same event.
  • Recipients are watchers and mentions. The actor does not notify themselves.
  • Rapid edits of one page collapse into one row.
  • The badge can be a few seconds stale. The list, once opened, is exact.

What I would say

  • One human action becomes one event, then many recipient rows. That fan-out is the design.
  • I would group by a key such as page plus verb, so twenty edits do not become twenty rows.
  • Preferences are checked before I write the inbox row, not after the user opens the bell.
  • Non-functional: mark-read is idempotent, the list is paged, and the badge does not poll every second.
  • Edge cases: a watcher removed before delivery, a mention of someone who cannot see the page, a burst on a popular page, and mark-read on two devices.

Two approaches

  • Fan-in at read time: store the event once and compute the inbox when the bell opens. Cheap to write, and the open becomes a heavy query.
  • Fan-out at write time into a per-user inbox. Writes cost more, and the bell is a cheap query. I would still skip fan-out for users who have been idle for a long time and build their first page on read.

I would pick fan-out for active users and fan-in for cold users. Is a slightly stale badge acceptable?

API design and schema

About minute twelve to twenty-two.

Questions

  1. Is the inbox read-heavy once we have paid the fan-out cost?
  2. Do we push the badge, or is SSE enough?
  3. Should mark-all-read be one call?

Contract

  • Notification: id, user id, group key, title, target URL, read time, and the rolled-up count.
  • Preference: user id, event type, channel, and quiet hours.
  • GET inbox with a cursor. POST read on one id. POST read-all with a timestamp so a race does not mark a newer row.
  • The badge is a count endpoint or a push. I would use SSE or a WebSocket, not a one-second poll.
  • A repeat POST read returns the same row. The client can retry safely.
  • If the user cannot see the target, I drop the notification rather than show a title they must not read.
  • Email is not this API. A worker reads the same event and sends mail if the preference says so.
  • Errors on the badge are soft. The last count stays, with no scary banner, until the list is opened.

Component design and scalability

About minute twenty-two to forty-two.

Questions

  1. Is the bell global chrome shared by every product?
  2. Do we virtualize the list from the start?
Event→Recipient resolve→Inbox row→Bell→List
  • While I draw: grouping happens before the row is written, not in the React list.
  • Opening the bell fetches the first page. Mark-read paints immediately and reconciles the count.
  • Local state is open-or-closed and which row is focused. Server state is the page and the count.
  • I virtualize if the page is long. Most people only need the first screen.
  • A flag can disable a noisy event type without a deploy.
  • The bottleneck is fan-out on a hot page, so I collapse the group before I write thousands of rows.
  • I would watch fan-out time, badge lag, and mark-read errors, with an SLO on time-to-open the list.

Scale-up and failures

About minute forty-two to fifty-two.

  • A page with a huge watcher list: group first, then write rows in batches. I do not notify idle accounts inline.
  • If the inbox store is down, the bell keeps the last count and the panel says notifications are unavailable.
  • If the event bus is delayed, the product still works. Notifications are not on the click path of editing a page.
  • Two devices mark read: the timestamp on read-all keeps them from fighting.
  • I retry badge connect with jitter. I do not reconnect in a tight loop after an outage.

Wrap-up

Under two minutes.

  • The center is a cheap read because we paid for fan-out, and we grouped before we wrote.
  • Active users get rows. Cold users are built on open. The badge is allowed to lag. The list is not.
  • We spend write capacity, and we keep the bell off the user's critical path.
  • I would roll out by event type and watch fan-out time and badge lag.

Confluence feed

Interviewer: design a feed of Confluence activity. Rank it from likes, shares, views, and who I follow. Do not drown me in every edit.

Requirements API Components Scale Wrap-up

Requirement gathering

About the first twelve minutes.

Questions, one at a time

  1. Is this following people and spaces, or every update in the tenant?
  2. Does following send mail, or is mail a separate watch?
  3. What is a card: one action, or one page with the actions rolled up?
  4. How do we rank: recency, popularity, or what I am likely to open?
  5. What scale: cards per user per day, and how fresh is fresh?
  6. Must every card be something I am allowed to open?

If they tell me to decide

  • Following does not send mail. Watching mail stays a different feature.
  • One card per page. Many edits in a short window collapse.
  • Rank is recency with a boost if I follow the author or I viewed the page before.
  • A page I cannot read never appears. Revoking access removes it on the next fetch.

What I would say

  • The feed is a ranked list of pages I am likely to care about, not an audit log.
  • I would roll activity up so a busy editor does not push the rest of the feed down.
  • Permissions are checked when I read the feed, so a revoke is not stuck until a rebuild.
  • Non-functional: stable cursor pagination, a first page that can come from cache, and no layout jump as counts update.
  • Edge cases: I unfollow mid-scroll, a page is restricted after I saw the card, a brand-new user with no follows, and a burst of edits on one page.

Two approaches

  • Pure fan-out on write: every follower gets the card pushed into a precomputed feed. Fast to read, and a popular author is an expensive write.
  • Pure fan-in on read: store the events and build the page when I open the feed. Cheap to write, and the open gets slow.

I would push to recently active followers and build the page on read for everyone else. Does a minute of lag on the feed bother you?

API design and schema

About minute twelve to twenty-two.

Questions

  1. Is the hot path GET the next page of cards?
  2. Do likes and views need to be live on the open card?
  3. What is the cursor: score plus id, so a new insert does not skip rows?

Contract

  • Card: page id, title, space, actors, a rolled-up verb, a count, a score, and a cursor.
  • Follow: user id and the target, which is a person or a space.
  • GET feed with a cursor. POST follow and DELETE follow. Those are rare writes.
  • I would not socket the whole feed. A refetch when I focus the tab is enough. Live counts can wait for the next page.
  • The cursor is opaque and ordered by score then id, so paging does not duplicate or skip.
  • If a card fails the permission check, I drop it and fill the page from the next candidates.
  • Empty feed for a new user returns a small set of suggested spaces, clearly marked as suggestions, not as activity.
  • Errors: a failed next page keeps the cards I have and offers retry. I do not blank the feed.

Component design and scalability

About minute twenty-two to forty-two.

Questions

  1. Is the feed a home page, or a panel beside the page?
  2. Do we virtualize the list?
Activity event→Roll up→Active followers→Feed page→Authz
  • While I draw: roll-up happens before the card is stored. The list just renders cards.
  • The first page can paint from a short-lived cache, then revalidate. I label nothing as live if it is not.
  • I virtualize the list. Images on cards lazy-load.
  • Follow and unfollow update local state immediately and reconcile. The next page uses the new follows.
  • A flag can switch a tenant from hybrid fan-out to pure fan-in if a hot author is too expensive.
  • The bottleneck is a popular author with many followers, so only active followers get a push.
  • I would watch time-to-first-card, permission-drop rate, and follow-write cost, with an SLO on first-page latency.

Scale-up and failures

About minute forty-two to fifty-two.

  • Ten times the events: roll-up harder, and cap how many followers receive a push. The rest see it on read.
  • If the feed service is down, I show the last first page from the client cache and pause new follows.
  • If authz is down, I would rather show a shorter page than show a restricted title.
  • A card whose page was deleted drops out on the next fetch. I do not leave a broken link as a permanent row.
  • I do not refetch the entire feed on one new event. I prepend or I wait for the next focus.

Wrap-up

Under two minutes.

  • The feed is ranked, rolled-up pages, not a firehose, and following is not mail.
  • Push to active followers, build on read for everyone else, permission check at read.
  • We accept a little lag, and we avoid both a slow open and a write storm.
  • I would ship to a slice of tenants and watch first-page latency and restricted titles that slipped through.

Mentions

Interviewer: design @mentions. Typing a name in a Jira or Confluence editor should find the right person or team, fast, and only people who belong in this context.

Requirements API Components Scale Wrap-up

Requirement gathering

About the first twelve minutes.

Questions, one at a time

  1. Are we mentioning users, teams, or both?
  2. Is the directory the whole tenant, or people already on this page or project?
  3. How large is the directory, and what latency do we want after a keystroke?
  4. Must every suggestion be someone who can see this page?
  5. Keyboard only, or mouse as well, and what does the screen reader hear?
  6. If suggest is down, can the editor still save plain text?

If they tell me to decide

  • Users and teams. Bias toward people already on this issue or page, then the directory.
  • A large tenant, tens or hundreds of thousands of accounts. Suggest stays under about three hundred milliseconds at p95.
  • I only suggest people who can see this content.
  • If suggest fails, the editor still works. I insert text and I do not block save.

What I would say

  • A mention is a structured token: type, id, and a display label. It is not a string we hope still matches after a rename.
  • I debounce, I abort the previous query, and I cap the list at about eight.
  • The first paint can be recent mentions from this session. The server list replaces it when it returns.
  • Non-functional: a combobox pattern, no request per key without a pause, and no download of the whole directory.
  • Edge cases: two people with the same name, a deactivated account, a team the user cannot see, and a query that arrives after a newer one.

Two approaches

  • Download the directory and filter locally. Instant after the download, and impossible at tenant scale, plus it leaks accounts.
  • A prefix query to the server, scoped by permission and biased by context. A small session cache for repeats.

I would pick the server prefix query. Should a deactivated account be hidden, or shown as inactive?

API design and schema

About minute twelve to twenty-two.

Questions

  1. Is this read-only and very chatty, with a tight limit?
  2. Do we need real time, or is a fresh query per pause enough?
  3. How do we store the mention inside the document or the comment?

Contract

  • Suggest request: query, context id such as page or issue, types, and a limit.
  • Hit: type, id, label, secondary text such as a team name, and whether they are already on this content.
  • REST, aborted when the query changes. No socket.
  • The saved body stores the id. The label is display-only and can be refreshed when we render.
  • I start the request after a short pause, around a hundred and fifty milliseconds, and I skip an empty query.
  • Cache key is user plus context plus query, in memory, for this session only.
  • A stale response is ignored if its query is not the current one.
  • Errors return an empty list with a flag so the UI can say suggestions are unavailable without blocking the keystroke.

Component design and scalability

About minute twenty-two to forty-two.

Questions

  1. Is this one picker used by the editor, comments, and Jira fields?
  2. Does the design system already have a listbox?
Editor→Mention picker→Suggest API→Directory prefix→Authz
  • While I draw: authz is on the suggest call. The picker never filters a full directory.
  • The picker is a combobox. Arrow keys move, enter inserts, escape closes, and focus returns to the editor.
  • I announce the count politely. I do not move screen-reader focus on every keystroke.
  • Recent picks are local state. Results are server state for the current query.
  • Insert replaces the @query with a token node so backspace deletes the whole mention.
  • The bottleneck is query rate on a large directory, so the prefix index stays on the server and the client sends one call at a time.
  • I would watch suggest latency, abort rate, and insert-to-save errors, with an SLO on time-to-results.

Scale-up and failures

About minute forty-two to fifty-two.

  • A hundred thousand accounts: prefix search, limit eight, context bias. I never page the whole company into the popover.
  • If suggest is down, I keep typing as plain text and I say mentions are unavailable.
  • If authz is slow, I would rather show a spinner than show a person who cannot see the page.
  • A rename: the stored id still resolves to the new label at render time.
  • I debounce so a fast typist does not stampede the directory.

Wrap-up

Under two minutes.

  • A mention is an id plus a picker, not a string search over a downloaded directory.
  • Debounced prefix query, permission-scoped, context first, editor stays usable if suggest fails.
  • We accept a short pause after a key, and we do not leak accounts or freeze the editor.
  • I would ship the picker in comments first and watch suggest latency and empty-result rate.
